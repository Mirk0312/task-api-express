## Decisión de permisos
- Rutas autenticadas: `/api/tasks` (GET, POST, PATCH) y `/api/auth/me`
- Ruta exclusiva de admin: `DELETE /api/tasks/:id`
- Justificación: Las operaciones estándar de consulta, creación y actualización de tareas pueden ser ejecutadas por cualquier usuario autenticado de forma legítima (`user` o `admin`). Sin embargo, las acciones destructivas o de alto impacto, como eliminar registros de la base de datos, se restringen exclusivamente a los administradores (`requireRole('admin')`) para preservar la integridad de los datos del sistema.

## Preguntas de cierre
1. **¿Por qué un token decodificable no necesariamente es un token válido?**
   Cualquier persona puede leer y decodificar la estructura del payload de un JWT (ya que solo está codificado en Base64Url), pero un token es criptográficamente válido únicamente si su firma coincide con la clave secreta del servidor y si el campo de expiración (`exp`) se encuentra vigente.

2. **¿Cuándo corresponde responder 401 y cuándo 403?**
   Se responde `401 Unauthorized` cuando el cliente no está autenticado o sus credenciales son ausentes, incorrectas o inválidas. Se responde `403 Forbidden` cuando el usuario sí está autenticado e identificado, pero su rol carece de los privilegios necesarios para acceder al recurso solicitado.

3. **¿Por qué CORS no sustituye la autenticación?**
   CORS es una directiva de seguridad del navegador orientada a controlar qué dominios externos pueden consumir los recursos de la API, pero no verifica la identidad de quien realiza la petición. Herramientas externas (como Postman o scripts de backend) pueden ignorar CORS fácilmente, mientras que la autenticación valida de forma segura la identidad del usuario a nivel de aplicación.

4. **¿Qué riesgo existe si DELETE se registra antes de requireRole?**
   Si el orden de los middlewares o controladores se altera incorrectamente, se podría permitir la ejecución de lógica de negocio o validación antes de validar que el usuario posea los permisos de administrador adecuados, comprometiendo la seguridad y el control de acceso del endpoint.

5. **¿Por qué debes iniciar sesión después de cambiar el rol en MongoDB?**
   Porque el token JWT contiene la identidad y los permisos (`role`) incrustados en su payload al momento de generarse. Actualizar el campo directamente en la base de datos no modifica el token previamente emitido que el cliente almacena, por lo que se requiere un nuevo login para obtener un token actualizado con el rol de `admin`.

6. **¿Cómo llega un error asíncrono de authenticate al errorHandler en Express 5?**
   Express 5 maneja de forma nativa las promesas rechazadas dentro de las funciones middleware y controladores asíncronos. Cualquier excepción lanzada con `throw` o pasada a `next(error)` es interceptada automáticamente por el framework y redirigida al middleware centralizado de manejo de errores.

7. **¿Qué limitación tiene el almacén en memoria del rate limiter al escalar la API?**
   Utiliza la memoria RAM de la instancia local del servidor. Al desplegar la API en un entorno distribuido o escalado horizontalmente (con múltiples contenedores o balanceadores de carga), cada instancia llevará un conteo independiente, lo que permitiría evadir el límite real rotando entre nodos. Para solucionarlo se requeriría un almacén compartido como Redis.

8. **¿Qué cambios requeriría autorizar por propietario de la tarea?**
   Requeriría añadir un campo de relación (por ejemplo, `userId` o `owner`) en el esquema de Mongoose de la tarea, asignarlo automáticamente con el ID del usuario extraído de `res.locals.auth` al momento de crear el registro, y ajustar las consultas del repositorio para filtrar y permitir modificaciones o eliminaciones únicamente si el `userId` coincide con el del propietario.

El desarrollo de esta actividad ayudó a comprender la importancia vital de separar las capas de autenticación y autorización mediante middlewares limpios y reutilizables.
